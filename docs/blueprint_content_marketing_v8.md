## Executive Summary

**「旅の問いに答えて信頼を作り、通信で回収する」**

この事業の資産はメディアでも記事でもなく、**構造化された旅行データ・コーパス**である — 店舗・手続き・交通・実価格・行列・通信環境 × 言語 × 確認日。これを yah.mobi 本体ドメインの上に置き、6つの出力面（ガイドページ／llms.txt／AIコンシェルジュ／アフィリエイター素材キット／yah.homes配信／**旅程キャンバス**）で配信する。

- **戦う単位は「ジャンル」ではなく「クエリ」**。ジャンル（グルメ・旅行情報）はどこも激戦だが、「言語×具体クエリ」（タイ語のローミング比較、韓国語のKakaoTalk認証不安、繁体字のVisit Japan Web解説）は空白である。空白は「類型」でなく「言語×類型」で判定する。
- **主軸は eSIM に近いクエリ層**: 王道（マネーページ8本）・eSIMグリッド・ローミング比較・旅のハウツー。高意図帯の記事在庫は約180本で、最初の18ヶ月分がこれで埋まる。
- **グルメは福岡限定の「堀」**（月2〜3本）。グルメメディアと同じ土俵（評価・網羅・話題性）では戦わない。食べログが構造的に持たない「訪日客の実用データ列」（行列・支払い・通信環境・ハラール検証）だけを実訪問で貯める。役割は直接転換ではなく、被リンク・AI引用の権威・再訪・yah.homes連携。
- **チャネルの序列**: コンテンツ＝資産エンジン、アフィリエイト＝配信網（鯨＝その最上位層。実績データで昇格させる）、まとめ買い＝**計画に算入しない上振れ**（購買行動が未証明のため）。
- **目標: 1,000本/月** = オーガニック500〜700本 ＋ アフィリエイト300〜500本の合算（§8）。目標シナリオでM24、保守でM30〜36。
- **判断の規律**: 意思決定は保守基準（成熟ラグ6ヶ月・CVR1%）で行う。M2/M3/M6/M12の検針カレンダー（§9）で「議論ではなく実測」で配分を替える。

## 3. アーキテクチャ（v8確定事項）

### 3-1. 本体ドメイン統合

コンテンツは yah.mobi 本体配下に置く。magazine.yah.mobi は使わない（公開前の今が移行コスト最小）。

**パスは「格子」と「編集コンテンツ」で分ける**（Wise・Zapierの実例に基づく・v8-1追加）。Wiseは通貨換算格子(`/currency-converter/usd-to-eur-rate`)を送金・口座と同格の一等市民パスに置き、ブログとは分離している。Zapierも組み合わせ格子(`/apps/{app}/integrations`)と編集記事(`/blog/`)を分けており、検索流入の主力は前者。うちも同様に分離する:

```
yah.mobi/esim/{lang}/{slug}      … 層M・0・1（王道・eSIMグリッド・ローミング比較 = 格子）
                                     機械的に拡張する構造化ページ。商品(/buy等)と同格の一等市民パス
yah.mobi/guides/{lang}/{slug}    … 層1.5・3（旅のハウツー・福岡実訪問 = 編集コンテンツ）
                                     取材・実訪問を要する記事群
```

分ける理由: ①格子は商品に近いほど権威が伝わりやすい ②機械的拡張（市場×キャリアの追加等）と取材ベースの編集運用はフローが異なり、パス分離でGA4の系統別計測・制作管理がしやすくなる。層をまたぐ内部リンク（/esim/ ⇄ /guides/）は双方向に張る（連動6要件②の実装形）。

理由: ①ガイドが稼ぐ被リンク・AI引用が**販売ドメインの評価**として貯まり、マネーページ・/buyの順位を底上げする ②AIの引用先＝店（引用と決済の距離が1） ③型Aの勝者（Wise・Zapier・Canva）は全てコンテンツを商品ドメイン上に置く ④計測・コーパス・Search Consoleの一元化。

### 3-2. 単一コーパス×4出力面（ヘッドレス構成）

```
[胴体] 編集システム（旧magazine v0.3・別Firebaseプロジェクト）
  品質ゲート15項目の構造化入力＋承認フロー＋記事Firestore
        │ 公開承認をトリガーに静的ビルド
        ├─ 頭①: yah.mobi/esim/ ・ /guides/ ページ群（SEO・AI引用）
        ├─ 頭②: llms.txt・構造化データ（外部AIへの直接配信）
        ├─ 頭③: AIコンシェルジュ（サイト内チャット・§3-5）
        ├─ 頭④: アフィリエイター素材キット（§6-2）
        ├─ 頭⑤: yah.homes 配信（関連記事のみ・§6-4）
        └─ 頭⑥: 旅程キャンバス（コーパスを旅程の文脈で手渡す・§3-6）
```

### 3-3. 編集＝別プロジェクト、公開＝本体（静的パブリッシュ）

- 公開ページは承認後に静的HTML化して本体Hostingへデプロイ（プリレンダ＝AIクローラー/SEOのSSR要件も同時に満たす）
- 編集者の権限・実験・障害が決済系に波及しない（爆発半径の分離）。公開面は編集システムへのランタイム依存ゼロ
- Firebase Hostingは別プロジェクトへのパスルーティング不可のため、この「ビルド時に渡す」構成が正解

### 3-4. 本体との連動6要件

1. **UI一体化**: 本体のデザインシステム・ヘッダー/フッター・言語切替を共有（ガイドが「別サイト風」に見えたら統合価値が毀損）
2. **双方向導線**: ガイド→店（ブリッジ・ウィジェット・/buy）だけでなく**店→ガイド**（プランページ→容量ガイド、購入完了→旅の準備、エラー画面→対処ガイド）
3. **価格の単一ソース**: ウィジェット・記事・llms.txtの価格は本体Firestoreから。記事と店の数字が1円でもズレたら信頼ごと壊れる
4. **購入状態との連動**: 認証は本体Authに一本化。**購入後こそガイドの出番**（設定・旅ナカ・トップアップ・紹介）
5. **言語整合**: ガイドの言語＝決済までの言語。KO記事→英語決済画面の段差はCVRを直撃する
6. **計測一体**: GA4プロパティ1つ・ユーザー単位30日窓で「ガイド閲覧→数週間後の購入」を接続

### 3-5. AIコンシェルジュ（段階導入）

- Phase 1: サイト全ページにチャット窓（自社コーパスでRAG。回答に出典記事・マップリスト・文脈が合えば /buy を添付）。**冷スタート問題なし**（訪問者は検索経由で既に来ている）
- 初日からファーストパーティのクエリログが貯まる＝「答えられなかった質問」リストが次に作る記事を教えてくれる（§4-3のクエリマイニング）
- Phase 2: 利用率・会話内CVRが実証されたら独立した目的地（chat.yah.mobi等）へ昇格を検討。**AIサイトを最初の一手にしない**（ChatGPTとの習慣競争になり配布で死ぬ）

### 3-6. 旅程キャンバス（出力面⑥・v8-2追加）

**一行定義**: 訪日客が電話できない/かけられない確認を、一次実測で資産化し、通信という最深ノード（eSIM）まで一続きに深く提供して、**旅の詰まりを消す道具**。コーパスの6番目の出力面であり、AIコンシェルジュ（§3-5）の自然な発展形。検索経由で来た訪問者に「旅程を組み立てる器」を手渡すため、冷スタート問題は§3-5と同じ理由で存在しない。

**なぜ作るのか（価値のレイヤーが一段上がる）**: AIの旅行提案は"資料"止まりになる — 状態を持たず・補正されず・決定が残らず・決済に繋がらないから（**L0＝生成**。ここはAIでコモディティ化）。価値は一段上の **L1＝取りまとめ**（状態を持ち・突き合わせ・補正し・決定を保持する層）にあり、回収は **L2＝eSIM/homes** で起きる。ただしL1が堀になるのは、取りまとめが①生成AIが見られないデータ（コーパス）で補正され ②ユーザーの実決定が蓄積し system of record になり ③決済に隣接している、時**だけ**。この3つを欠いた"取りまとめUI"は劣化Wanderlogで、AIエージェントに食われる。

**相互作用モデル＝編集キャンバス（補正エンジンではない）**: AIとコーパスは候補（カード）を供給するだけで、**人間が手で並べ替え・確定・確認事項をクローズする**。理由: ①自分ごとの旅程で人は黒箱の自動修正を信用しない ②人間主導なので精度不足でも壊れない ③実決定が器に溜まる（乗り換えコスト） ④「人が実際にどう旅程を組むか」が露出し、**クエリマイニング（§4-3）の一次データ**になる（コンシェルジュログと同じ金鉱を、旅程の組み立てログとして得る）。

**カードと記事は親子ではなく兄弟**: カードも記事も同一コーパスPOIの投影（§3-2ヘッドレス）。カード→記事（深く読む）、記事→カード（「旅程に追加」）の双方向（連動6要件②の拡張）。同一ソースなので確認日・価格が更新されると**両方同時に変わりズレない**（要件③）。カードは3種類あり、段階的に光る:

| カードの種類 | 記事連動 | 例 |
|---|---|---|
| 記事あり × コーパスあり | フル双方向 | 実測データ＋記事化済みの店 |
| コーパスのみ（記事まだ） | 事実は載る／「続きを読む」は薄い | 実測はあるが記事化前のPOI |
| フリーテキスト | 連動なし | 「移動日」「Session」等（利用者の任意メモ） |

フリーカードを常に許容し、コーパス/記事がある所だけ深く光る設計にする（**汎用骨格＋訪日で光るレイヤー**の、カード単位の実装）。「よく追加されるのに記事がないPOI」＝**次に書く記事の信号**（§4-3のループがPOI単位で回る）。

**eSIMは附随ではなくコーパスの最深ノード**: 「通信環境」はコーパスの一列であり、eSIMはその答え。「この店は電波△」→「だからeSIM/トップアップ」は一続きの思考で、抱き合わせ（クロスセル）ではない（引用と決済の距離1）。日数×人数（旅程が持つ状態）が固まった瞬間に**層0「用途」の提案**が成立する。

**戦場と勝ち筋**: 編集キャンバスにした瞬間、競合はChatGPT（生成）ではなく **Wanderlog/Notion（キャンバス）** になる。キャンバスのUXでは勝てない — **器は薄く作り、そこで差別化しない**。勝ち筋はただ一つ、カードにコーパスの事実（現金のみ・行列・通信環境・確認日）が"貼りついている"こと。強みは「ローカル情報の広さ」ではない（それは食べログ/Google/Wanderlogが持つ＝網羅戦で負ける）。強みは **Googleが載せない実用列を、一次実測＋確認日で、訪日客の言語で、狭く深く持ち、自社決済に繋がる**「深さ×狭いfootprint」。

**利便性の定義（スコープの規律）**: 利便性＝**訪日客の"詰まり"を消すこと**。詰まり＝電話できない・言語・通信・支払い。ここから外れる便利さ（天気・航空券比較・汎用ガイド）は足さない — 足すと超アプリ化しWanderlog/Googleと網羅戦になり負ける。

**導入段階（爆発半径ゼロ）**: §3-5 Phase 1（コンシェルジュ＋RAG）に「**旅程トレイ（保存かご）**」を足す最小形から。記事のマップリスト/コンシェルジュ回答から「行きたい」をかごに入れる→日別に並べる→LINE/Kakaoで共有→3日埋まったらeSIM ○GB提示→ドリップ（§8-2レバー3）の受け皿。既存コーパス＋コンシェルジュ＋ドリップの再合成なので新規事業ではなく、初日から「旅程の組み方」という一次データが溜まる。独立の目的地（独立アプリ）への昇格は§3-5 Phase 2と同じ規律で実証後に判断（**AIサイト/独立アプリを最初の一手にしない**）。

**位置づけの注記（ドッグフーディングの二層）**: 骨格（比較→確定→確認事項クローズのループ＋日別スロット/ホテル/同行者/費用のデータモデル）は共通資産で、コーパス連動レイヤーだけ訪日に効く。骨格は運営者自身の旅行で磨けるが、コーパスの強みは**コーパスがある場所（福岡・訪日）にしか宿らない**。二兎を「層」で分ける（§3-6の設計原則）。

**この出力面が体現する事業定義**: 本アプリの価値は確認の"**代行**"（依頼ごと・1確認＝1顧客・線形・労働）ではなく確認の"**資産化**"（一度確認→構造化→全員に配布→鮮度維持・1確認＝N顧客・償却が効く）である。旅程キャンバスは、その資産の**最もおいしい配り方**（旅程という文脈で手渡す）の一つ。

## 5. 転換設計と検証

- **CVRの構造**: ブレンド目標（保守1%／目標1.45%）は「層Mが刈り取る」合成値。集客層の仕事は内部送客（10〜20%）と保存。「記事→購入クリック20%超」のような一段抜き想定は置かない
- **計測単位**: GA4ユーザーコンバージョン・30日窓で固定（保存→再訪型の転換をセッション単位で取り漏らさない）
- **動的価格ウィジェット＋/buy/:slug**（v7方針⑧）: ブリッジ直下・記事末尾に実勢価格・Airalo差額をSSRで焼き込み（現地通貨・取得日時併記）。`?ref=` パススルーは実装必須要件
- **記事内購入の順序**: まず遷移型（/buyポップアップ）＋4段計測（クリック→ドロワー→ログイン→購入）で漏れ段を特定 → 数字が正当化したらウィジェット内プラン選択 → フル記事内購入は最後
- **検証広告プログラム（M1〜2・総額10〜15万・終了日固定）**: 「客を買う」のではなく「答えを買う」。①マネーページCVR実測（3〜5%仮説） ②グループKWの需要実在 ③タイ語市場ボリューム ④LP・ウィジェット文言A/B。出稿前に「答えるべき質問」を書く。一般KWの頭には行かない（AOV¥3,000では競合の高AOV×世界LTV×調達資金に競り負ける — 構造的に模倣不能な土俵）

### 5-1. 価格ポジション：構造的コスト優位を前提とした「最安を楔に」戦略（v8-2追加）

§5冒頭の「一般KWの頭には行かない」は、**コスト優位を持たない一般的な挑戦者への警告**である。yah.mobile は次の構造的コスト優位を持つため、その**例外**として「最安」を集客の楔（フック）に取りに行く:

- **一人運営・低間接費** — 競合の重い間接費・投資家リターン要求がない → 身軽な薄利で回る
- **magazine・道具の自作** — 開発外注費ゼロ・反復が速い（優位そのものが安く武器化できる）
- **IIJ直接契約（将来）** — アグリゲータ（eSIM access）の上乗せを外し、**日本SKUの原価そのものを下げる**

**楔と堀の時系列**:

1. **身軽フェーズ（今）**: 一人・自作の薄利で「**日本eSIM最安**」を楔に取る。武器は自作で安く作れる — **正直な比較表（§4-1-1）＋ llms.txt 動的価格・Airalo差（§1-2）**。主要帯で本当に勝つため透明性がそのまま説得力になり、価格クエリ（「일본 이심 최저가」等）が **AI引用の主砲**になる（数値で引用率+40%・§1-3）。
2. **ボリューム到達 → IIJ直接**: 卸原価が構造的に下がり、**楔（matchableな薄利）が堀（追随困難な原価）に変わる**。

**規律（この戦略の前提条件）**:

- **薄利であって赤字ではない** — 調達資金を持たないため、**原価割れの消耗戦はしない**（下回れば Airalo/Saily の資金力に競り負ける）。最安は「身軽ゆえの薄利」で作り、損失で買わない。
- **価格は楔、コーパスは堀** — 日本SKUは IIJ直接まで matchable。**最安だけを堀にしない**。最安＝初回獲得、コーパス・信頼・利便性＝LTV（リピート・homes・紹介）。
- **自作のスループット上限を直視** — 技術・間接費は自作で安いが、**記事1,000本/月の労働は自作で消えない**（§7）。最安の原価計算にスケール時の記事労働をタダで入れない。
- **IIJ移行の閾値を数字で持つ** — 「ある程度のボリューム」を検針（§9）で追う実数（月間販売量／データ総量）として定義し、直接契約の交渉開始トリガーにする。

## 6. チャネル統合

### 6-1. 序列（v8確定）

**コンテンツ（資産エンジン）→ アフィリエイト（配信網）→ 鯨（アフィリエイトの最上位層）**。鯨は独立プログラムとして営業しない — ref実績で月10本以上売る人が現れたら、その人にだけコラボ記事・独占レポート・専用特典を投資する（「実績データが鯨を教えてくれる」）。まとめ買い・リピートは計画非算入の上振れ。

### 6-2. アフィリエイター素材キット（v7継承）

公開承認済み記事からAIが自動生成: ref付き記事URL・`/buy/:slug?ref=` ディープリンク＋QR・SNS転載テキスト＋OGカード（多言語）・数値レポート引用パック。パートナー素材ページはM3計測基盤とセットで実装（それまでは手動発行）。獲得営業はしない — 記事資産で武装した「向こうから来る」アフィリエイトに限る（VAコールドアウトリーチはBase赤字の実証済み失敗パターン）。

### 6-3. 市場別の配信出口

- **韓国=Naver前倒し（Phase 2→M2〜3）**: KO記事10本が溜まり次第、Naverブログ転載を開始。最大市場の主戦場をGoogle待ちにしない
- 台湾・タイ=LINE共有最適化、香港・星・尼=WhatsApp（共有モジュール1つでロケール別出し分け・v7 §11-5継承）
- 大手エディトリアル（TimeOut等）は広告を買わずPRレーン: 数値レポートを記事として書かせる（earned media=ChatGPT引用源51%＋被リンク）
- Cheapo型の独立系クエリメディア: アフィリエイトレーン（25%はAiralo標準10%の2.5倍 — 鯨級への最強の提案材料）

### 6-4. yah.homes への配信（関連性の高い記事のみ・v8追加）

コーパスの出力面⑤。**eSIM系（層M/0/1）は配信しない**（宿泊サイトの文脈に合わない。eSIMはフッターのクロスCTAに留める）。配信対象は関連性タグで選別する:

| 配信対象 | 例 |
|---|---|
| 層3: 福岡実用データ | 物件周辺の店・行列実測・支払い情報・ハラール検証 |
| エリア・交通ハウツー | 空港→市内・地下鉄・タクシーアプリ・コインロッカー |
| 季節 | 桜・祭り・旧正月の営業状況 |

**配信は2形式**（SEOの共食いを防ぐ設計が肝）:

1. **記事シンジケーション**: 該当記事を yah.homes にも掲載。**canonical は必ず yah.mobi/guides/ の原本に向ける**（配信対象は層3・ハウツー・季節=/guides/ 系のみ。層M/0/1=/esim/ 系はhomesに配信しない §6-4冒頭のとおり。重複コンテンツとして両ドメインが共倒れするのを防ぐ。homesでの役割は宿泊検討者への価値提供であって検索順位ではない）
2. **コーパス再合成型「物件周辺ガイド」（本命）**: 物件の位置 × コーパスのPOIデータ（店舗・行列・通信環境・確認日）から**物件ごとの周辺ガイドを自動生成**。複製ではなく再合成なので重複問題が構造的に発生せず、「この宿から徒歩5分の、現金のみ・行列は金曜19時〜の店」という**他のどの宿泊サイトにも存在しないページ**になる。室内QR（旅ナカ導線）の受け皿もこれ

CMS実装: 品質ゲート項目14（層/言語）に**配信先フィールド（guides / homes / 両方）**を追加。承認フローは同一（公開承認1回で対象面すべてに静的パブリッシュ）。

効果: ①yah.homes の予約検討者に対する周辺情報の厚み（宿選びの決め手） ②宿泊ゲストの旅ナカ体験（QR→周辺ガイド→eSIMトップアップ） ③eSIM⇄homes のクロスセルが双方向になる ④自社プロパティ間の自然な相互リンク。

## 9. KPI・検針カレンダー

**規律（v7 §8注記継承）**: 42ヶ月シートは目標シナリオ（ラグなし・CVR1.45%）。**Go-NoGo・投資判断は保守基準（成熟ラグ6ヶ月・CVR1%）で行う**。M1〜6のモデル未達はSEO上のデフォルトであり失敗のシグナルではない。逆に目標達成で慢心しない。

| 検針 | 見るもの | 決めること |
|---|---|---|
| **M2** | 検証広告の答え（マネーページCVR・グループ需要・TH需要） | CVR仮説の答え合わせ・TH前倒し判断の材料 |
| **M3** | タイプ別CVR・内部送客率・在庫表100行の消化・AI引用初観測・Naver初速 | **月10本の配分組み替え**（§4-2） |
| **M6** | インプレッション曲線・保守基準Go-NoGo・鯨級1件目 | 継続/配分見直し/撤退線（§10） |
| **M12** | 王道クエリの順位トレンド・拡張vs深化（§8-4）・ベトナム判断 | 後半戦の投資先 |

KPIの持ち方: ブレンドCVR1本ではなく**層別CVR＋内部送客率（10〜20%）＋層M訪問シェア（20%目安）＋メッセンジャー/AI経由比率**に分解（どの段が外れたかをM3から特定できる形）。AI引用は月次20クエリ×言語×エンジン別の目視記録＋GA4参照元。

## 10. リスクと対応

| アフィリエイトが鯨級ゼロのまま | M6検針で判定。25%条件＋素材キットで2〜4件が現実ライン。ゼロならオーガニック単独計画（M30〜36）に切替 |

| 品質ゲート形骸化（外注体制の宿命） | 公開承認（週30分）だけは外注しない。承認ログで追跡 |
| 編集者の離脱 | SOP・在庫表・品質ゲートが属人化を防ぐ（v7から継承） |
