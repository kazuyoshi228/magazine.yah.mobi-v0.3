## Executive Summary

**「グルメで信頼を作り、通信で回収する」**

magazine.yah.mobi は、日本在住チームにしか書けない**グルメ一次情報**（実訪問・実価格・実写真・地図）で訪日旅行者とAI検索エンジンの両方から信頼を獲得し、少数精鋭の**マネーページ（eSIM比較・購入導線）8本**で回収するコンテンツファネルである。

- **グルメ記事 = 集客とAI引用の資産**（月10本の6割を投下）。AIは一次情報を引用せざるを得ない。
- **v7追加: グルメ記事は「個店・クラスタ記事」（鮮度が武器・更新コスト高）と「グルメ体験ガイド」（居酒屋の入り方・食べログ/予約アプリの使い方・ハラール対応——陳腐化しにくく、ターゲット言語ではSEO空白）の2層で構成**する。
- **マネーページ = 回収装置**（8本×多言語だけを最高品質で維持）。全グルメ記事から通信ブリッジで内部リンク。
- **福岡 = 旗艦クラスタ**。在住地の情報深度で「誰にも負けない都市」を1つ作り、yah.homes クロスセルも最大化。**在住地であることは個店記事の鮮度管理コスト（閉店・価格改定への追随）でも競合に対する構造優位**である。その後、東京・大阪へ展開。
- **v7追加: 拡散の主戦場はメッセンジャー**（台湾・タイ=LINE、韓国=KakaoTalk、香港・シンガポール・インドネシア=WhatsApp）。グループ旅行の意思決定が起きる場所に「共有される単位」（マップリスト・しおり・投票カード）を送り込む。

グルメが主軸である根拠: 訪日旅行者の「したいこと」ランキングで「日本食を食べる」は常に1〜2位であり、eSIM購入動機（快適にスマホを使いたい）の用途の筆頭がグルメ検索・地図ナビ・予約・QR注文である。**グルメコンテンツはeSIMの「使い道」を具体的に見せる最強のコンテンツ**であり、集客と回収が同一文脈に乗る。

**チャネルの序列（v7確定・2026-07-10）: magazine（SEO/AI引用）＝主戦略・資産エンジン、鯨BD＝キャッシュブリッジ、アフィリエイト＝magazine資産の配信網。** 記事は止めても売り続け・複利で効き・コミッションを渡さない自社資産であり（42ヶ月累計はシナリオ中最大）、アフィリエイトは独立戦略ではなく素材キット（§5）で記事資産を配る流通レイヤーとして使う。ただしこの序列はM3のCVR実測・M6のAI引用実測（Go-NoGo判断）で検証するまでは「勝ち筋」であって「勝ち確」ではない。

財務上の位置づけ（42ヶ月シート・magazineシナリオ）: magazine は「遅いが複利で効き、止めても資産が残る」長期エンジンであり、単体の速効性を求めない。鯨BD（早い・大きい）との統合シナリオで先行赤字を吸収する。数値は42ヶ月シートを単一ソースとする。

## 1. 環境分析：AI引用時代の勝ち筋

### 1-1. AI検索がコンテンツに与える影響（2026年時点の実勢）

| コンテンツ類型 | AI検索の影響 | v7の扱い |
|---|---|---|
| 設定・HowTo（eSIM設定手順等） | **最悪**。AIが回答内で完結、ゼロクリック化。 | 主軸から降格。マネーページの一部として維持のみ |
| 一般情報（eSIMとは等） | 悪い。AI回答で完結 | 作らない |
| 比較・購買直前（おすすめ・比較・料金） | 中程度。AI回答に引用+購入はサイトで発生 | **マネーページ8本に集約** |
| **一次ローカル情報（グルメ・現地の今）** | **良い**。AIは生成できず引用元を必要とする。鮮度が武器 | **主軸。月産の6割** |
| **グルメ体験ガイド（文化・アプリの使い方・ハラール）** | **言語による**。英語ではAI回答で完結しがちだが、**タイ語・インドネシア語ではAIの学習素材自体が乏しく、引用元になれる**。スクリーンショット・実体験を含めれば一次情報化する | **v7新設。ターゲット言語で作る耐久資産**（§11-3） |
| ブランド指名（yah.mobile とは） | 影響なし | llms.txt・比較データで担保（実装済み） |

### 1-2. yah. が既に持っているAI引用アセット

- **yah.mobi/llms.txt（実装済み）**: 実勢プラン価格・Airalo との価格差を動的生成してAIクローラーに提供。「日本のeSIMで最安は？」への回答素材を自ら供給している。
- **magazine の器（実装済み）**: 多言語・カテゴリ・Schema対応構造・購入CTA。
- 今後追加: magazine.yah.mobi/llms.txt（記事一覧の自動反映）、FAQPage/HowTo/Article Schema の全記事付与（v5 §4の5条件は引き続き有効）。

### 1-3. 競合の空白（v6分析＋言語軸で拡張）

- **競合eSIMメディア（Airalo/Holafly/Saily のブログ）は日本のグルメ一次情報を構造的に書けない**（日本在住チームがいない）。実際にAiraloの日本記事は「10 Must-Try Foods」「7日間モデルコース」等の汎用英語ガイドのみで、実訪問・実価格・店舗単位の情報はゼロ（2026年7月確認）。
- **v7追加: 言語の空白**。コンテンツ類型として飽和していても、ターゲット言語では空白であるものが多い（§11-3のマトリクス参照）。例: タイ語の「東京 ラーメン おすすめ」、インドネシア語の「大阪 ハラール レストラン」、タイ語・英語の「食べログの使い方」はほぼ競合不在で、AI引用可能性も高い。
- 韓国・台湾の旅行ブログは情報が古く、通信への導線を持たない。「実訪問した最新のグルメ情報 × その場で必要な通信」を一体で書けるのは現状 yah. だけである。

### 1-4. 競合のAIファースト実態とGEOの実測データ（2026年7月調査・v7追加）

| 競合 | AIファースト対応 |
|---|---|
| Airalo（最大手） | **ほぼ無対策**。llms.txtなし（404）・robots.txtにAIクローラーへの記述なし。ブログは英語の汎用リスト記事のみ |
| Holafly | **llms.txt実装済み**（2026年6月更新・多言語の商品/目的地カタログ）。ただし中身は商品ページ列挙で、引用に値する一次情報はゼロ |
| Saily（NordVPN系） | 外部エージェントに403を返す強いbot遮断。AIクローラーを巻き込んでいる可能性（自滅型リスク） |

GEO（生成エンジン最適化）研究の実測（2026年）:
- **llms.txtは導入ドメインの97%で取得リクエストがゼロ、引用頻度との相関も未確認**。llms.txt合戦は勝負所ではない（保険として維持はする）
- 引用率を実際に上げる要素: **統計・数値の記載（+40%）、定義文で始める書き方（+2.1倍）、専門家引用（+115%）**、直接回答ブロック、明確な見出し階層
- **エンジンごとに引用源がほぼ重ならない**（ChatGPT⇔Perplexityの引用ドメイン重複は11%）。ChatGPTは獲得メディア（earned media）51%、**PerplexityはReddit 46.5%**、Claudeは長文編集記事を好む
- AI検索経由の流入は**オーガニック検索の約4倍のCVR**（本戦略の経済性を裏付ける）

結論: 隙は「AI対応の有無」ではなく一段深い層にある。**「AIが引用せざるを得ない一次データ（数値・統計・確認日付き）を、エンジン別の引用経路（Schema/PR/Reddit）ごとに置く」**こと。具体施策は §11-8。

## 2. ペルソナ（v7: 6市場に対応して再定義）

**ジヨン（韓国・26歳・会社員）**: 友人3人と初の福岡週末旅。Instagram と Naver で「후쿠오카 맛집（福岡グルメ）」を検索、**KakaoTalkのグループで旅程を共有**。屋台ともつ鍋の行き方・並び方・予算を知りたい。→ 福岡グルメ記事（韓国語）→ 通信ブリッジ「行列状況はGoogle Mapsでリアルタイム確認。データは大丈夫？」→ eSIM購入。

**シャオメイ（台湾・32歳・夫婦旅行）**: 大阪・京都・福岡10日間、**訪日4回目のリピーター**。PTT/Dcard と ChatGPT で「日本 美食 行程」を調査、**LINEで夫とマップリストを共有**。定番は行き尽くしており「観光客が知らない店」を探している。福岡では一棟貸しに泊まりたい。→ 「2回目以降の福岡」記事（繁体字）→ yah.homes クロスセル ＋ 10日間データ容量のマネーページ → 両方購入。

**ニン（タイ・27歳・バンコクの会社員）**: ソンクラーン休暇に友人4人で東京・大阪8日間。タイ語で「โตเกียว ราเมน（東京 ラーメン）」を検索するが、タイ語の信頼できる情報がほとんどない。**旅程はLINEグループで決める**。→ タイ語グルメ記事（競合ほぼゼロ）＋「食べログの読み方」ガイド → 容量見積り付きモデルコース → 4人分まとめてeSIM購入。

**アイシャ（インドネシア・30歳・ジャカルタ・夫婦＋子1人）**: 初訪日。**ハラール対応が最大の関心事**で、Instagram と WhatsAppグループ（家族・ママ友）で情報収集。「確認済み」でない情報は信用できない。→ ハラール実訪問検証記事（英語→将来ID語）→ キッチン付き yah.homes（自炊ニーズと好相性）＋ eSIM。

補足: **香港**（リピーター率が高く「2回目以降」軸とWhatsApp共有が有効）と**シンガポール**（英語・高消費・ミシュラン/ホーカー文化で食への関心が極めて高い）は、シャオメイ（リピーター軸）とニン（英語圏はEN記事）の変奏として §11-1 の市場表で扱う。

全ペルソナの共通項: **「食」が旅の目的で、食情報の検索・共有が旅マエ〜旅ナカに集中し、その全場面で通信が必要**。そして**意思決定はメッセンジャーのグループ内で起きる**。

## 3. コンテンツアーキテクチャ：Hub & Spoke

### 3-1. 二層構造（v7: Spokeを2系統に分割）

```
【グルメクラスタ（Spoke）— 月産の6割・AI引用と集客の資産】
  A. 個店・クラスタ記事（鮮度が武器・更新コスト高 → 福岡集中）
     屋台・ラーメン・もつ鍋・鮮魚・うどん・清川高砂ローカル・
     空港から市内・yah.homes周辺 …「在住者の今」を武器に
     → 東京クラスタ → 大阪クラスタ（Phase 2〜）
  B. グルメ体験ガイド（陳腐化しにくい耐久資産・ターゲット言語で空白）
     居酒屋の入り方・食べログ/Googleマップの読み方・予約アプリの使い方・
     QR注文/モバイルオーダー対応・ハラール/ベジタリアン対応・
     日本の食マナー …テンプレート化して多言語量産
        │
        │ 通信ブリッジ（全記事に設置）
        ▼
【マネーページ（Hub）— 8本×多言語だけを最高品質で維持】
  1. 日本eSIM完全ガイド（購入〜開通）
  2. iPhone設定 / 3. Android設定（HowTo Schema）
  4. Airalo比較（llms.txtの価格データと連動）
  5. 日数×用途別データ容量シミュレーション
  6. 繋がらないときの対処法
  7. トップアップ方法
  8. FAQ 30選（FAQPage Schema）
  → yah.mobi 購入フロー
```

v5の56本リストは資産として維持するが、カテゴリA(20本)は上記8本に統合・圧縮する。**マネーページは「数」ではなく「鮮度と網羅性」で勝つ**（公開後も毎月更新。iOS/Android の新バージョン対応、価格改定の即日反映）。

**A/Bの使い分け原則（更新コストの管理）**: 個店記事（A）は閉店・移転・価格改定で陳腐化が早いため、**在住地の福岡に集中**させ鮮度管理コストを構造的に下げる。遠隔クラスタ（東京・大阪）では個店単発よりエリア・ジャンル別ガイドと体験ガイド（B）の比率を上げる。Bは文化・使い方が主題のため陳腐化しにくく、LLMでの多言語展開・テンプレート量産に向く。

### 3-2. 月産10本の配分（編集者1名体制・v7改訂）

| 種別 | 本数/月 | 役割 |
|---|---|---|
| グルメ一次情報A: 個店・クラスタ（福岡→東京・大阪） | 4本 | 集客・AI引用・yah.homes連携 |
| グルメ一次情報B: 体験ガイド（文化・アプリ・ハラール） | 2本 | 耐久資産・TH/ID語空白の先取り・通信ブリッジとの親和性最大 |
| マネーページ新規 or 大規模更新 | 2本 | 回収装置の維持（8本完成後は更新に充当） |
| 旅行×通信（季節性：桜・ソンクラーン・旧正月・紅葉・年末） | 2本 | 季節検索の刈り取り |

グルメ合計6本（6割）は v6 から不変。財務モデルの入力値（月10本・月¥18万）も不変。季節枠は四半期に1本を数値資産レポート（§11-7①）に充当する。制作分担（AI下書き×人間裏どり）と月15本への拡大条件は §11-8 に従い、拡大時はシートを更新する。

### 3-3. グルメ記事の品質基準（AI引用の生命線）

品質は2段のゲートで担保する。**①投稿必須項目**（CMSの入力欄として実装し、未入力では物理的に公開できない）と、**②記事作成時チェックリスト**（編集者が企画〜公開後まで使う作業手順）。①はシステムが強制し、②は人が確認する。この2つのゲートは、承認フロー（§11-8: 企画承認→AI下書き→裏どり→公開承認→投稿）の各ステータス遷移の通過条件としてCMSに実装する。

#### 3-3-1. ウェブ記事の投稿必須項目（未入力では投稿できない）

CMS/入稿テンプレートの必須フィールド。1つでも空欄なら公開ボタンを押せない仕様とする（実装されるまでは編集者＋Yoshiレビューで代替運用）。

| # | 必須項目 | 形式・条件 | 目的 |
|---|---|---|---|
| 1 | 訪問日 | 日付（記事内にも明記） | 一次情報の証明・AI引用シグナル |
| 2 | 実価格・実メニュー | 撮影した価格表・伝票の画像＋本文記載 | AIが生成できない一次データ |
| 3 | オリジナル写真 | **5枚以上**（ストック写真は不可） | 一次情報の証明 |
| 4 | 地図・アクセス | 地図埋め込み＋最寄駅/行き方 | 旅ナカ利用・ローカルSEO |
| 5 | 営業時間・定休日 | 確認日を添えて記載 | 鮮度・信頼性 |
| 6 | 行列傾向 | 曜日×時間帯の目安 | 「在住者の今」の差別化 |
| 7 | **通信環境メモ（v7追加）** | 店内電波状況・Wi-Fi有無・QR注文/モバイルオーダーの有無・整理券アプリの要否 | 「この店に行くならデータ必須」の一次証明（§11-2 方針④） |
| 8 | 通信ブリッジ | 「スマホがその場で必要になる場面」の具体記述＋マネーページへの内部リンク | 回収導線（本戦略の生命線） |
| 9 | 直接回答ブロック | 冒頭に検索意図への直接回答（7ブロックテンプレート準拠）。**定義文で始め、数値を必ず1つ以上含める**（例:「博多の屋台は中洲・天神に約100軒。予算は1人¥2,000〜3,000——」） | AI引用・ゼロクリック耐性（定義文+2.1倍・数値+40%の実測則。§1-4） |
| 10 | FAQ | **3問以上**（FAQPage Schema対象） | AI引用・ロングテール |
| 11 | Schema Markup | Article＋FAQPage（HowTo記事はHowTo） | 構造化データ |
| 12 | CTAリンクの計測パラメータ | 全CTAに `?ref=` / UTM 付与（§4） | 記事単位のCVR実測 |
| 13 | 公開日・更新日 | 更新日はリライトのたびに更新 | AI引用の主要シグナル（§6） |
| 14 | カテゴリ・対象言語 | クラスタ（福岡/東京/大阪…）＋記事系統（A個店/B体験ガイド/マネー/季節）＋展開言語 | Hub & Spoke管理 |
| 15 | **Googleマップ保存リスト（v7追加・A記事必須）** | 記事掲載店を収録した公式マップリストのリンク | 旅ナカ再訪・共有・通信ブリッジ（§11-2 方針②） |

※ 個店・クラスタ記事（A）は1〜15すべて必須。体験ガイド（B）は1〜6を「情報の確認日・出典・実機スクリーンショット」に、15を「関連リスト（任意）」に読み替える。マネーページ・季節記事も同様に読み替えて適用する。

## 4. 転換設計（v5 §3を継承・実装条件を追記）

- 7ブロックテンプレート・CTA配置・通信ブリッジ・yah.homes クロスCTA は **v5の設計をそのまま採用**（§5・§7は有効）。
- 追加①: 全CTAリンクは `?ref=` / UTM を必須とし、**M3実装（affiliateCode 計測基盤）とGA4で記事→購入の実CVRを記事単位で計測**する。CVR実測が出た時点で、財務モデルのCVR入力（現状1.45% = オーガニック1%にGEO施策のAI経由比率15%×CVR4倍を織り込んだブレンド値。シート「前提条件（入力）」B46・2026-07-10更新）を実測値に置換する。**1.45%は目標シナリオ値であり（AI経由CVR4倍は早期導入者の報告値・AI経由比率15%はM12目標）、意思決定は保守基準CVR1%で行う（§8注記）**。
- 追加②: グルメ記事中心のミックスはCVRが1%を下回る可能性がある（TOFU比率上昇）。**感度: CVR 0.6%なら magazine 単体の42ヶ月損益は約±0**。ゆえにマネーページ8本の品質と通信ブリッジの文面テストが本戦略の生命線であり、月次でブリッジ文面のA/Bを回す。
- **v7追加③: CVRを高めるのは「文脈の近さ」**。網羅リストより状況別決定支援、記事よりマップリスト・容量見積り付き旅程（§11-2）。記事単位CVRを系統（A/B/マネー/季節）×形式（リスト/旅程/ガイド）で比較し、高CVR形式に配分を寄せる。
- **v7追加④: CVRの構造 — ブレンドは「マネーページが刈り取る」数字（2026-07-10追記）**。目標CVR（保守1%/目標1.45%）は全記事一律ではなく、タイプ別の合成で届く: **マネーページ 3〜5%**（実質ランディングページ。競合アフィリエイトの成約率3〜7%と同性質）× 訪問シェア20% ＋ **グルメ記事 0.3〜0.5%**（ブリッジ・ウィジェット込み）× シェア70% ＋ 季節・旅程 1〜2% × シェア10% ≒ ブレンド0.9〜1.5%。**グルメ記事の仕事は直接転換ではなく、①マネーページへの内部送客（クリック率10〜20%が現実的な目標）と②マップリスト保存による再訪の仕込み**。「記事→購入リンクのクリック率20%超」のような一段抜きの想定は業界実勢（インラインCTAで3〜10%）に反するので置かない。
- **v7追加⑤: CVRの計測単位はユーザー単位で固定（2026-07-10追記）**。旅行者の購買サイクルは旅マエ数週間〜2ヶ月であり、「保存→旅ナカ再訪→購入」の転換は**セッション単位のCVRでは初回訪問が転換ゼロに見える**。訪問→購入CVRは **GA4のユーザーコンバージョン（30日アトリビューション窓）** で定義し、M3計測基盤の設計に固定する。この定義が曖昧だと、M6のGo-NoGoで「達成していたのに未達に見える」誤判定が起きる。

### 11-2. CVRを高めるキュレーション方針（7方針）

CVRの原理: **購買瞬間に近い文脈ほど転換する**（発見型リスト < 状況別決定支援 < 旅程・容量見積り < 比較）。網羅ではなく決定支援でキュレーションする。

| # | 方針 | 内容 | なぜCVRが上がるか / 空白性 |
|---|---|---|---|
| ① | 状況別の決定支援 | 「福岡ラーメン20選」ではなく「雨の日に並ばず入れる3軒」「深夜1時から食べられる3軒」「予約なしで入れる人気店の回り方」 | 旅ナカ検索（=通信使用中・購買直前/直後）に刺さる。AIは「今の状況」を生成できない |
| ② | **Googleマップ保存リスト添付（最優先）** | 記事掲載店をyah.公式マップリストとして配布し「保存」をCTA化。リスト説明文にも通信ブリッジ | 保存リストは**旅ナカで必ずデータ通信とともに開かれる**。AIに記事を要約されても価値が残る資産。競合ゼロ |
| ③ | データ容量見積り付きモデルコース | 「福岡2泊3日食い倒れコース—使う通信量は約3GB（地図/翻訳/QR注文の内訳付き）」→ マネーページ#5へ直結 | 旅程は購買文脈そのもの。容量見積りが比較・購入への自然な橋になる |
| ④ | 「通信が主役になる店」特集 | QR注文のみの店・地下で電波が弱い店・整理券/順番待ちアプリ必須の店・翻訳必須の店を実訪問でタグ付け（§3-3-1 #7） | eSIMの必要性を一次情報で「証明」する記事群。実訪問が要るため競合が構造的に書けない |
| ⑤ | グループ（同行者）単位 | 「4人で行くもつ鍋の予算と頼み方」「幹事向け3日間食プラン」 | 読者の背後の同行者全員がeSIM候補。まとめ買い導線（§5）と直結 |
| ⑥ | ムスリムフレンドリー×一次情報 | ハラール/豚・アルコール不使用を実訪問で検証し「確認日」付きで公開 | インドネシア（+マレーシア波及）。宗教的要請ゆえ「確認済み」の信頼が絶対条件＝AI生成で代替不能。競合完全空白 |
| ⑦ | リピーター向け「2回目以降の福岡」 | 「観光客が知らない、在住者の行きつけ」。清川・高砂ローカルはこの軸の旗艦素材 | 台湾・香港のリピーター8割超に刺さる。指名検索・メッセンジャー内の口コミ転送と相性が良い |
| ⑧ | **価格と購入を記事の中へ（動的価格ウィジェット＋購入ディープリンク）** | 記事の通信ブリッジ直下/末尾CTAに実勢価格・Airalo差額をSSRで焼き込み表示（現地通貨換算・取得日時併記）。CTAリンク先は本体の共有用購入リンク `/buy/:slug`（プラン確定済みドロワー直開・設計図 2026-07-10）に `?ref=` を付けて統一 | 「記事→比較ページ→購入」の2ホップを1ホップに短縮（§4追加③の文脈の近さ）。数値の常時更新はAI引用+40%則にも効く。llms.txtのBuy URL併記でAIエージェントがプラン単位で購入案内可能に——競合に存在しない層。※クライアントJS挿入はAI/検索クローラーに見えないためSSR必須（§11-7④） |

優先実装順: **②（マップリスト）→ ③（容量見積りコース）→ しおりページ（§11-5）**。いずれもM1〜2の福岡クラスタ制作にそのまま織り込む。

### 11-3. SEO・AI引用の空白地帯マップ（言語×コンテンツ類型）

コンテンツ類型として飽和していても、ターゲット言語では空白のものが多い。**空白は「類型」でなく「言語×類型」で判定する**。

| コンテンツ例 | 言語 | 競合状況 | AI引用可能性 | v7の扱い |
|---|---|---|---|---|
| 「東京 ラーメン おすすめ 2026」 | タイ語 | ほぼ空白 | ◎ | TH展開時の初期弾（§11-6） |
| 「大阪/福岡 ハラール レストラン」 | インドネシア語/EN | ほぼ空白 | ◎ | 方針⑥。EN先行で即着手 |
| 「京都 抹茶スイーツ 食べ歩き」 | 韓国語 | 中程度 | ○ | 一次情報（実訪問・実価格）で差別化 |
| 「食べログ/Tabelogの読み方」 | EN・タイ語 | 空白に近い | ◎ | 体験ガイドB。実機スクリーンショットで一次情報化 |

### 11-7. AI引用の獲得経路（GEO施策・§1-4の実測に基づく）

llms.txt競争ではなく「引用せざるを得ない一次データ × エンジン別経路」で取る。

| # | 施策 | 内容 | 根拠・狙い |
|---|---|---|---|
| ① | **数値資産の定期発行（最優先）** | 実訪問データを統計化して四半期発行:「福岡屋台 実勢価格インデックス」「訪日客のQR注文遭遇率調査」「都市別・旅程別データ消費量実測」。プレスリリース配信とセット | 統計は引用率+40%。競合に一次データは皆無。PR経由でメディア掲載されればChatGPTの主要引用源（earned media 51%）にも乗る。llms.txtの実勢価格提供の思想を「調査レポート」へ拡張 |
| ② | エンジン別チャネル | **Perplexity対策=Reddit**（r/JapanTravel等で透明性あるブランド参加・実データでの質問回答。ステマ禁止、コミュニティ規約準拠）／**ChatGPT対策=①のデジタルPR**／**AI Overviews対策=Schema+直接回答**（対応済み） | 引用源はエンジン間でほぼ重ならない（重複11%）。記事を書くだけではPerplexity（Reddit 46.5%）には載らない |
| ③ | 文体ルール | 直接回答ブロックは「定義文で始め、数値を必ず含める」（§3-3-1 #9に規定済み）。見出し階層・箇条書きの徹底 | 定義文+2.1倍・数値+40%。コストゼロで全記事に効く |
| ④ | AIクローラーの技術的受け入れ | GPTBot/ClaudeBot/PerplexityBot/Google-Extended等をrobots.txt・WAF/CDNで明示allow。**記事はサーバーサイドレンダリング必須**（AIクローラーの多くはJS非実行。SPAのままでは全戦略が無効化される） | Sailyの403型自滅を避ける守り。アーキテクチャ設計の最重要要件として引き継ぐ |

運用: ①は季節枠（§3-2）を四半期に1本充当して制作。②のRedditは編集者の週次30分から小さく開始し、AI引用計測（§8）で効果が見えたら拡大。計測は月次20クエリをエンジン別（ChatGPT/Perplexity/Gemini/AI Overviews）に記録する。

### 11-8. 制作分担とスケール（AI下書き×人間裏どり・月10〜15本体制）

**採用する分担**（v7確定）:

| 工程 | 担当 | 内容 |
|---|---|---|
| 下書き（執筆・多言語展開・Schema/FAQ/OGP/しおり素材・**アフィリエイター素材キット（§5）**の生成） | **AI** | 7ブロックテンプレート＋文体ルール（定義文＋数値）を自動適用。**下書きの全記述に出典URLを必須添付**——出典のない記述は編集者が機械的に削る（幻覚対策）。素材キットは公開承認後に自動生成 |
| 裏どり（価格・営業時間・固有名詞・閉店/移転の確認） | **人間（編集者）** | 出典URL付き下書きを一次資料と突合。信頼性の最終責任は常に人間 |
| 現地訪問（実価格・実写真・通信環境メモ・訪問日） | **人間（編集者/Yoshi）** | 代替不可（§3-3-1 項目1〜7）。月2回の福岡訪問枠 |
| 編集行為（ディレクション・最終チェック・写真選定・公開判断） | **人間（編集者）** | 品質ゲート15項目（§3-3-1）の判定者。CMSバリデーションが補助 |

#### 承認フロー（v7確定・CMSで強制する）

```
① 企画          … AIが企画キューを提案 or 人間が起票
     ↓ ★企画の承認【人間: Yoshi/編集者】採否・方向づけ
② 下書き        …【AI】出典URL必須。A記事は実訪問の素材を反映
     ↓
③ 裏どり        …【人間: 編集者】出典突合・「要現地確認」の解消。
                   裏どり完了チェックなしでは次へ進めない
     ↓ ★承認【編集権限を持つ人間: 編集者/Yoshi】
                   品質ゲート15項目（§3-3-1）＋写真選定の最終判定
④ 投稿（公開）  … 承認済み記事のみ公開可能
```

**CMS実装要件**（アーキテクチャ設計に引き継ぐ）:
- 記事ステータスの状態機械: `企画 → 企画承認済み → 下書き済み → 裏どり済み → 承認済み → 公開`。**段階の飛ばし・逆行は権限者の明示操作以外で不可**
- ロール権限: 「企画承認」「裏どり完了」「公開承認」はそれぞれ人間のロールにのみ付与（AIやスクリプトには付与しない）。公開ボタンは編集権限ロール＋全ゲート通過時のみ活性化
- 各承認に承認者・日時のログを残す（誰がいつ通したかを追跡可能に）
- 多言語版・リライトも同一フローを通す（リライトは①をスキップし③から）

**工数と規模**: 1本あたりの人間工数 = 裏どり30〜60分＋編集30〜60分（＋A記事は訪問）。**月10〜15本なら人間工数は月15〜30時間で、編集者1名で回る**。この分担はAI側に検証エージェント等の仕組みを作り込む必要がなく、**M1から始められる**（CMS実装までは、ステータスをスプレッドシート/Notion等の進行表で代替運用）。

| 記事タイプ | 月10本（Base・§3-2） | 月15本（拡大時） |
|---|---|---|
| A: 個店・クラスタ | 4本 | 5本 |
| B: 体験ガイド（TH/ID/KO優先。ENでの文化ガイド量産は§11-3に抵触） | 2本 | 5本 |
| マネーページ新規/大規模更新 | 2本 | 2本 |
| 季節・数値資産レポート | 2本 | 3本（うち四半期1本はレポート） |

多言語展開込みのアウトプットは月40〜75本（1原稿→4〜5言語に増幅）。

#### 常時稼働の2デーモン（本数より価値が出る自動化・人間の裏どりの補助）

- **鮮度監視デーモン**: 全掲載店の営業時間・閉店情報を毎日クロールし、変化があれば記事更新を**自動起票→編集者が判定・承認**して「更新日」が動く。更新日はAI引用の主要シグナル（§1-4）であり、個店記事の陳腐化リスク（§9）への直接の回答。**記事が汎用的な競合には更新対象自体が存在せず、構造的に模倣不能**。
- **裏どり素材の事前収集**: AIがソース横断のファクトシート（出典URL・ソース間の食い違い箇所）を裏どり前に用意し、人間の裏どり時間を短縮する。判定はあくまで人間。「食い違い→現地確認リスト」は**取材の照準器**として月2回の福岡訪問の密度も上げる。

#### 拡大の条件

- **月10本→15本**: 編集者の実測工数が月30時間以内に収まっていること。**42ヶ月シートの入力値を更新する**（月間記事数 B44: 10→15。制作コストB47への影響はAPI費用のみで軽微）— 財務モデルと現実の乖離を作らないこと。
- **月30本（1日1本）は将来オプション**: 人間の裏どりのままでは破綻する（月45時間超）ため、裏どりを「AIがファクトシートを作り、人間は矛盾箇所の判定・承認のみ」に切り替え、§3-3-1の15項目を機械チェックする検証エージェントを整備した場合にのみ検討する。CVR・AI引用の実測で増産系統（特にB）の寄与が証明されていることが前提。

**量産は戦略ではなく、検証済みモデルの増幅である**。
